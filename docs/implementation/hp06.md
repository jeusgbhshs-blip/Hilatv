# HP06: server delivery readiness, distinct from generation completion

This branch is stacked on HP05 `00e05bb`, HP04 `149bfd7`, and their HP08 reader dependency. It changes worker/shared policy and version handling only. HTTP preview/download/export/share routes are integrated by the parent task; this commit does not impose an HTTP-wide ban on previews. No paid/model requests, environment files, deployments, global installations, or existing user projects were used.

## Public server contract

```python
from workers.workflow.readiness import readiness

view = readiness(snapshot, state=None, media=None)
```

`snapshot` is the server-owned project record after normal API ownership checks. `state` optionally supplies the server checkpoint; omitted state is loaded from this project's node files. `media` optionally supplies an exact local project file; omitted media uses the current preview/deliverable pointer. Local containment and a fresh file stat are checked on every call. No body-provided path, quality flag, final-review JSON, or human-release flag can stand in for the private evidence documents.

The result is JSON-compatible:

- `delivery_status`: `ready`, `preview`, `needs_verification`, or `unavailable`.
- `quality_pass`: true only for a formally deliverable film. `status=completed` is never sufficient.
- `preview_available`: actual video/container decode success, independent of formal delivery. A mock/mixed/unknown film can have a valid playable preview.
- `media_provenance`: `live`, `mock`, `mixed`, or `unknown`; absent/contradictory evidence is conservative.
- `media_hash`: SHA-256 of the exact file; `media_path` is an internal canonical path and must be omitted from public API JSON.
- `reasons`: an array of `{code, message}` with Chinese explanations. Inspection also returns size/duration/codec/fps/frame dimensions when available.

Formal delivery retains H.264 MP4 and 30fps requirements. The existing 7.5 final-review line and hard-fail rules remain unchanged. Preview eligibility is not based on a passing review or a filename alone.

## Two internal writers; neither is an HTTP endpoint

`record_render_context(project_id, media, state, *, applied_draft_context=None)` is an N15 consumer hook. It runs only after a successful actual composition, measures the exact file, and writes `render-evidence/<sha256>.json`. N15 activities now call it. Each render attempt has its own server-generated directory, so a failed/new preview cannot overwrite the previous media file.

The hook records the actual supplied input context. A saved canvas is **not** an execution graph. The default applied projection is empty. The hook now explicitly rejects claims that N15 consumed saved clips, references, wires, or node parameters: their render consumers do not exist yet. Only a narration projection matching the actual supplied script and take can be acknowledged. In particular, saving a `timeline_clips` edit does not cause the old film to acquire a new render-input proof. A review writer cannot repair that gap by reading today's canvas after the fact.

A review attempt whose input context has no matching render witness is kept in `review-attempts/` for audit and does not replace a prior valid version's evidence for the same movie bytes.

`record_delivery_evidence(project_id, media, final_review, *, state, media_provenance, logo_evidence, ai_label_evidence, authorization_evidence, source_evidence=None)` is the later real-review hook. It writes `reviews/<sha256>.json`, bound to the project, current enterprise, exact media hash, and input/draft context. Readiness reads these private files; passing an apparently valid review in `snapshot`/`state` does not grant a release.

## Draft edits and immutable versions

The context includes the supplied script, narration/takes, audio track, aligned edit/timeline, selected candidates, brand, packaging, and license uses. Only selected candidates enter the content fingerprint; trying an unselected candidate does not revoke the existing film's review.

The server's current `canvas.json` contributes saved narration, prompt suffixes, reference uploads, clip order/in-out points, and content parameters/semantic wires connected to a shot/final/production input. Unconnected idea nodes are not treated as the execution graph. Positions, viewport, layout-version counters, regen counters, and candidate lists used only for alternatives are excluded. Moving nodes therefore does not cause a new model review. Changing connected content while the movie bytes remain unchanged produces `review_context_changed`/`draft_not_rendered` and preserves the old preview.

Versions save their canvas snapshot and content projection alongside their node/media snapshot. An immutable historical movie is checked against its archived content projection, so today's editing does not relabel that old movie as a newly approved draft or make its old review disappear. Restore swaps the canvas transactionally with nodes/media/master and uses the existing crash-recovery journal. Hash-mismatched version files are rejected before replacing the active tree.

Restore never writes an archived enterprise identity, consent archive, fee ledger, review document, audit log, or regeneration counter back over current controlled records. Private review/source evidence remains project-global and current; the copy in a version folder is for audit only. Current voice/portrait consent is rechecked from the enterprise archive, used license rows must match their authorized grants, expiry is rechecked against today's date, and current source settlement is re-read from the controlled evidence. Thus revocation, expiry, ownership changes, or a source being marked uncertain still block an older version. `last_ready_version_id` is computed from currently valid version readiness.

Human release only permits work to continue. It does not manufacture quality/source/authorization proof, and its exact media hash remains marked for a fresh review even when an older review existed. Only a new complete trusted verification can clear that marker. Reruns retain the previous preview pointer and file while generating a new candidate.

## Cache and performance

Expensive media inspection is cached by project id, resolved authorized path, device/inode, byte size, `mtime_ns`, and `ctime_ns`. Containment/stat happen before a cache lookup on every request. Hashing streams the file; ffprobe and full decode have bounded subprocess timeouts. Content/replace/restore changes invalidate naturally; render and restore also explicitly invalidate the cache. Cache entries are not reused across project authorization scopes. Review, draft, rights, date, and current consent checks remain outside the media cache.

Repeated status/Range gate calls do not rehash or decode the movie. The cache regression verifies five repeated checks create no additional media subprocesses; changing bytes while restoring mtime still invalidates via ctime. Media inspection restricts demuxers/protocols and does not follow network playlists. Project-directory symlink aliases and media symlinks escaping the authorized project cannot acquire a preview from a cached inspection. Current source settlement queries remain outside the media cache.

N15 now requires every spoken shot's take even when a mix is supplied, reads those actual sources, checks narration alignment/content against the narration stem, and checks that the supplied mix really contains its declared stems. The follow-up uses only fake gateways, original local audio/video fixtures, and isolated SQLite call/reservation rows; it does not require a real supplier.
